## Our situation

We are building a "deployment loop" for a quadruped: server-side teacher model -> edge student model -> quantized eval (latency/memory/power/success-rate) -> independent safety sentinel -> shadow deployment -> restricted closed loop. Authoritative plan: docs/design/2026-08-05-dog-deployment-loop-plan.md (v3.3). Facts base: docs/design/2026-08-03-dog-integration-plan.md (v2).

## The blocker that triggers this question

The B2 we have on site has been wrapped by a system integrator (Topsee). Their vendor support has now told us, in writing:
1. They do NOT recommend third-party direct Unitree DDS access; concurrent commanding causes abnormal motion. They offer instead their own "status forwarding" (telemetry) and "operation control interface" (motion command) APIs. Contract details for those APIs are still UNKNOWN (frequency, latency, deadman, velocity readback, authority handover).
2. Network topology: their upper computer (industrial PC) and the Unitree dog are on the SAME segment; all other devices are deliberately on DIFFERENT segments to avoid broadcast storms disturbing motion control. So they will likely refuse to put our machine on the dog's motion network.
3. Our planned D0 acceptance test (10 min continuous /sportmodestate DDS subscribe, then E4's four-step Move authority protocol) is therefore SUPERSEDED by vendor policy, not merely waiting for site scheduling.

Net effect: on the integrator-wrapped B2 we cannot currently validate the fast channel (continuous vx/vy/omega_z at 10-50Hz), the motion-level abort chain, or high-rate proprioception. The plan's D7 (restricted closed loop) is BLOCKED.

## What we need to validate end-to-end (7 requirements)

R1. High-frequency state subscribe: pose + velocity + IMU + proprioception, with timestamps, at a rate and jitter good enough for a 50Hz gate (observation age budget <=300ms, ideally far less).
R2. Continuous velocity command: vx/vy/omega_z at 10-50Hz, with documented deadman (stop sending -> dog decelerates to zero) and actual-velocity readback to confirm STOP.
R3. Sentinel/arbiter running on an edge computer, process-isolated from the model process (UDS datagram IPC), single command exit enforced by token + static scan.
R4. Edge inference of a quantized student model, with measurable latency / memory / power.
R5. Episode recording with time alignment (RGB + depth + action + state), QA-checkable.
R6. Safety: physical e-stop, speed box, virtual corridor / geofence.
R7. Navigation to waypoints (we can keep using a vendor/platform for this, or use open SLAM) — lowest priority.
