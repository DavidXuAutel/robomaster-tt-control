## Plan refresh proposal

### 1. 修改总体架构结论

将原来的：

```text
Topsee HTTP 慢导航 + Unitree DDS 状态/Move 快通道
```

改为：

```text
Topsee HTTP：任务下发
Topsee MQ：任务进度与结果
Topsee 状态转发：受支持的遥测源
Topsee 运控接口：候选快命令源，验证前禁用
Unitree DDS：实验性/停用适配器，不属于生产路径
```

保持 I3/I4 的意图：导航和快控制互斥。但把 `unitree_cmd_enabled` 泛化为 `motion_cmd_enabled`，不要把仲裁器永久绑定到 DDS。

### 2. DDS telemetry 与 DDS Move

逻辑上必须拆开，政策上暂时都禁用：

- **DDS Move：立即从生产候选路径移除。** 不再做当前 E4 小幅 Move 实验。
- **DDS subscribe-only：保留现有代码但默认关闭。** 只有厂商明确书面允许只读订阅，并给出网卡、topic、频率和网络约束后，才能重新安排只读测试。
- 即使以后允许只读 DDS，也不能推导出 DDS Move 获准；两者应有独立配置、独立门禁和独立验收。
- 不删除已完成的 `DdsTransport`，但文档必须标为“非生产、未获厂商支持、禁止现场启用”。

### 3. G10 成为候选快通道

是的，DDS Move 永久禁用后，G10“运控接口”成为唯一合理的厂商支持快通道候选。但只有满足以下条件才能承担 WAM：

- 连续全向速度控制，而非离散网页按钮；
- 稳定达到所需频率，且 P95/P99 时延满足闭环预算；
- 有明确的命令有效期或 deadman；
- 有可靠 STOP，且可读回实际速度确认停止；
- 有官方控制权获取、释放和导航互斥流程；
- i7 故障或网络断开时能自动安全停；
- 状态转发的频率、时间戳和延迟足够闭环；
- 厂商明确支持第三方长期调用。

任一关键项不满足，WAM 只能保持 shadow/dry-run，不能做真机闭环。不要把低频 HTTP 遥控包装成“快通道”。

### 4. 到点判定优先级

推荐顺序：

1. **主证据：MQ。**  
   必须同时满足：消息与当前 instruction/point 唯一关联、结果码明确表示成功、消息新鲜且顺序有效。不能只判断 `complete=true`。

2. **第一 fallback：`getCurrentByRobotId`。**  
   仅在重新设计后的 E1 真机验证通过，并采齐 G2 状态枚举后启用。否则保持 `UNKNOWN`。

3. **第二 fallback：状态转发的地图位姿距离。**  
   只有状态转发提供可靠位姿，并完成 G13 坐标系、地图原点、航向单位和时间戳验证后使用。不要再依赖直接 DDS pose。

4. **全部不可用：fail closed。**  
   MQ 断流、无法关联或结果语义不明时应报告 `nav_status_unknown/result_stale`，不得靠超时猜测已到达。

原 E1 应改成：

> `sendNavigate → MQ 指令关联 → 进度 → 成功到达/失败/取消` 全链路验证；同时观察 `getCurrentByRobotId`，仅评估其 fallback 资格。

### 5. 网络与进程位置

首选仍是 **B2 i7 用户机**，但这是待厂商确认的部署候选，不是已确认事实。成立条件是：

- 厂商确认该 i7 就是允许第三方部署的用户计算机；
- 它能通过受支持路由访问 HTTP、MQ、状态转发和运控接口；
- 不需要自行桥接狗体运动网与其他设备网；
- 不在 i5 平台机安装或修改任何东西。

禁止为了 DDS 测试自行把 i7 接入或桥接狗体网段。厂商已经明确提到网络风暴可能导致运动异常，这应上升为网络安全红线。
