### Repository findings that materially change the decision

The current `adapters/dog_unitree.py` is not a complete R1 implementation:

- It subscribes to native `rt/sportmodestate` and `rt/lowstate`.
- It replaces the robot’s source timestamp with local `time.monotonic()`.
- It keeps sport position, planar velocity, yaw rate, and IMU RPY, but discards accelerometer/gyro data.
- It keeps only joint position `q`, discarding `dq`, estimated torque, temperature, loss counters, and other proprioception.

So even on an open Go2 EDU, R1 needs adapter work before it is satisfied.

The current transport also imports:

```python
unitree_sdk2py.go2.sport.sport_client.SportClient
```

That is correct for Go2 but not B2. The current official Python SDK has a separate B2 client at `unitree_sdk2py.b2.sport.sport_client.SportClient`. `Move`, `StopMove`, and `Damp` have compatible signatures, but the complete API is not identical: B2 exposes `SwitchGait`, `BodyHeight`, and `MoveToPos`; the current Go2 Python client lacks those same methods and uses API 1036 for `Heart`. See the current [Go2 client](https://raw.githubusercontent.com/unitreerobotics/unitree_sdk2_python/master/unitree_sdk2py/go2/sport/sport_client.py) and [B2 client](https://raw.githubusercontent.com/unitreerobotics/unitree_sdk2_python/master/unitree_sdk2py/b2/sport/sport_client.py), checked 2026-08-07.

Required compatibility changes would therefore include:

1. Parameterize robot family and import the correct SportClient.
2. Add an explicit per-family capability table instead of assuming one API surface.
3. Preserve the device timestamp alongside receipt monotonic time.
4. Preserve IMU acceleration/angular velocity and motor `q/dq/tau/temp/lost`.
5. Check RPC return codes; `Move` is a no-reply call in both current clients.
6. Pin a tested SDK commit and firmware combination.

The positive part is that Go2, B2, B2-W and Go2-W use the same `unitree_go` low-level IDLs, while G1 uses `unitree_hg`. Unitree’s simulator documents that distinction explicitly. [Unitree MuJoCo](https://github.com/unitreerobotics/unitree_mujoco), checked 2026-08-07.

## What transfers to B2 / what does not

### Transfers

From Go2 EDU to a stock B2:

- `unitree_go` IDL concepts and `rt/sportmodestate`/`rt/lowstate`.
- The narrow `Move(vx,vy,vyaw)`, `StopMove`, `Damp` abstraction.
- DDS freshness monitoring and data-loss injection.
- Arbiter state machine, lease/token rules and I1–I15.
- UDS model-to-gate isolation and model-death behavior.
- Recorder/QA/replay schema and failure detection.
- ONNX/TensorRT export and benchmarking methodology.
- Speed-box, acceleration/jerk limit and virtual-corridor implementation.
- The structure of the E4 readable/controllable/deadman/no-preemption protocol.

### Does not transfer

- Topsee’s status-forwarding or operation-control API.
- Authority ownership between Topsee and the Unitree controller.
- Target B2 deadman, StopMove/Damp effectiveness or actual stopping distance.
- The integrator’s network segregation and broadcast restrictions.
- B2 firmware and SDK service configuration.
- B2’s 60kg dynamics versus Go2’s approximately 15kg mass.
- Payload-dependent stability, slips, stair/terrain response and actuator thermal limits.
- Camera placement, intrinsic/extrinsic calibration, occlusion and vibration.
- B2/i7 power and thermal measurements.
- Topsee E1/E3 semantics, mission cancellation, map alignment and navigation state.
- The student policy’s success rate or safe operating envelope.
- Target D7.

So the thesis should be phrased as:

> Go2 EDU validates the software safety architecture and development workflow. It does not validate the B2 system safety case or a B2 policy.

That distinction matters because the motion-level abort chain is exactly the part now hidden behind Topsee.

## Risks

- **No documented Unitree deadman.** Empirical Go2 success would not prove B2 or Topsee behavior.
- **Soft stop versus physical E-stop.** `L2+B` damping is useful but not a safety-rated physical disconnect. Cutting power to a standing quadruped can itself cause a hazardous fall.
- **Authority race.** Any interface without atomic lease/handover is disqualifying.
- **Firmware lock-in.** Freeze firmware and SDK commits. Do not accept OTA during validation. Do not assume downgrade is possible.
- **SDK drift.** The Python SDK is source-installed, depends on CycloneDDS 0.10.2, and its Go2/B2 surfaces already differ. Pin and regression-test.
- **Procurement delay.** Go2 EDU mainland lead time is unverified; B2/X30/M20 lead times are unverified.
- **Regional/export restrictions.** NVIDIA lists Jetson under ECCN 5A992.c and lists China SKUs, but current stock is unverified. Spot screens purchasers against US denied-party lists; mainland delivery is unverified. [NVIDIA FAQ](https://developer.nvidia.com/embedded/faq) and [Boston Dynamics sales policy](https://bostondynamics.com/faq/), checked 2026-08-07.
- **Rental mismatch.** A cheap Go2 Pro event rental is not a developer platform.
- **False confidence.** The largest risk is passing thousands of Go2 tests and mentally converting that into B2 safety evidence.
- **Compute integration.** A developer kit mounted on a moving robot needs approved power, cooling, vibration restraint and networking.
- **Navigation distraction.** R7 should remain last; a good Nav2 demo does not prove R1/R2/R6.
- **Plan-governance risk.** A vendor API can supersede DDS technically, but it does not supersede the written D0/D7 acceptance criteria without an approved plan revision.
