本文只做两件事：**记录已验证为真的操作路径**，以及**修正该方案接口基线中被实测推翻的条目**。

## 0. 一句话结论

在 2420 实验室用拓普视离线一体机完成一次「单点派单 → B2 自主导航到点」，
92 秒走完 6.58 m（含原地右转约 124°），肉眼确认到位。
**实验 E1 有结论：单点派单确实产生可查任务**，D7 门禁第 1 项的前置事实已具备。
同时暴露 10 个坑，其中 3 个会让调用方把失败当成功。

**当日下午追加一轮往返测试（§1.2），拿到本文最重要的一条结论**：
正午阳光直射前置深度相机会产生 `0.02~0.03 m` 的**假障碍读数**，避障把狗摁在原地，
而平台照样记 `result=成功`。**平台会在机器人零位移的情况下报成功**——
这比 §4 原先记的「result 不可单独判成败」严重一档，任何自动化闭环都必须有
独立于平台的位移校验，否则会把「完全没动」当成「任务完成」继续往下走。

### 1.1 交叉验证到的一个自洽点

重定位后，从底图检出的柱子中心 `(-0.46, 6.51)`（Ø1.15 m）反推狗朝向 **77°**，
算得机身中心到柱面 1.97 m；狗头相机实测 1.61 m，差值 0.36 m 恰为头部相机前置量。
**这条几何自洽是判定「重定位真的成了」的独立证据**，比看图标位置可靠——
建议后续每次重定位后都做一次这种交叉核对。

### 1.2 下午往返测试时间线（假停障的完整证据链）

| 时刻 | 动作 | 时长 | 停障告警 | 实际是否移动 |
|---|---|---|---|---|
| 11:01 | 派单 P3→P4 | 92 s | 无 | ✅ 走通 |
| 11:26 | 派单 P4→P3 | 63 s | 无 | ✅ 走通 |
| 11:32 | 派单 P3→P4 | 183 s | **持续报 0.03 m** | ❌ **一步没动**，`result=成功` |
| 11:36 | 派单 P4→P3 | 63 s | 持续 | ❌ 一步没动，`result=成功` |
| 11:59 | 派单 P3→P4 | 90 s 门禁中止 | **持续报 0.02 m** | ❌ 一步没动 |
| 12:06 | Body Control 摇杆原地转 90° | — | — | ✅ 转成功（链路是活的） |
| 12:08 | 派单 P3→P4 | 85 s | 无 | ✅ 走通 |
| 12:15 | 派单 P4→P3 | 85 s | 报 1 次即恢复 | ❌ 没到位，`result=成功` |

现场核实：报 `0.03 m` 时**机器人正前方物理上空无一物**，且狗**正对窗户**，时间为正午。

判读：
- **假障碍源自强光**。深度相机正对窗/阳光时饱和，返回近乎 0 的垃圾距离。
  这解释了三个特征：与朝向强相关、间歇发作、正午高发。
- **持续报 vs 瞬时报要区别对待**。12:15 那次只报 1 次即恢复，狗仍走了一段；
  11:32/11:59 是持续报，狗完全动不了。**判据应是「停障告警是否持续」而非「有没有出现」。**
- **Body Control 能动 ≠ 导航能动**。12:06 摇杆转向成功，证明平台→狗的运动链路完好，
  从而把故障域收敛到导航栈的避障判断。**这是一个廉价且决定性的分诊手段，建议固化进排障流程。**

## 3. 已验证的操作 SOP

### 3.0 前置

- 端点、账号、`robotId`、`deployment=offline` 等见 `configs/dog/topsee.json`（不入库真实值）。
- 口令走环境变量 `TOPSEE_PASSWORD`，**禁止写入代码、文档或 artifact**。
- 离线一体机的 API 前缀是 `/service`（不是 `/service/api`），登录走 JSON body，
  令牌头 `tuopushi_edge_token`——这些 `adapters/topsee_client.py` 已处理。

### 3.1 加载地图（派单的硬前置）

```python
c.load_map(robot_id, keyname)   # free/mapUpdate action=6
```

`keyname` 取 `map_meta.json` 的 **`keyNameMap`**，不是 `keyname` 也不是 `mapId`。
取错不会报错，只会静默空转。

验证方式：查告警表，确认此后不再新增「机器人还没有加载地图」。

### 3.2 重定位（唯一可靠路径 = 大屏 UI）

**不要用 API**（见 §4）。走界面：

1. 后台系统 → **Robot Monitoring** → 地图面板左下 ⚙ → **Map Settings**
2. **Quick Operations → Redirect**（拓普视把"重定位"叫作"重定向"）
3. 地图先放大；勾 **Show Point Arrows** 便于核对朝向
4. **第一次左键点击 = 机器人真实位置；第二次点击 = 机器人朝向**
5. 两点距离**不要太远**（远了报 `Redirect too far`），一两米的屏幕距离即可
6. 若提示「请先加载此地图后再进行重定向」，先点 **Load Map**

成功判据：图标贴合真实位置、箭头方向对、激光点云贴合墙线，
并按 §1.1 做一次几何交叉核对。

### 3.3 发单前检查（四项，缺一不发）

| 项 | 期望 |
|---|---|
| `robotState` | `02`（空闲） |
| `currentTaskId` | 空字符串 |
| 告警表 | 加载地图后无新增「还没有加载地图」 |
| `battery` | 留足余量（本次发单时 37%） |

### 3.4 派单与追踪

```python
c.send_navigate(robot_id, points_id)        # 返回体无 taskId，正常
# 约 3 s 内：getStateData().currentTaskId 出现 taskId，robotState 02 → 03
# 结束后：robotState 回 02，currentTaskId 清空
# 结果详情：GET instrument/robotTask/getPagingRobotTask
```

`getPagingRobotTask` 单条任务里有用的字段：
`result` / `resultState` / `status` / `alarmCount` / `duration` / `endDate` /
`normalCount` / `abnormalCount` / `instruction`（每个航点带 `completeTime` 与 `complete`）。

⚠️ **成败判据必须交叉核对**，只看 `result` 会误判（§4）。

### 3.5 中止手段（三层，从快到慢）

1. 遥控器 **长按 `L2 + B`** 软趴（未按 START 也有效，已实测）
2. Body Control 面板摇杆旁的 🔴 **STOP**
3. 平台 `instrument/robotTask/stopTask`

### 3.6 分诊流程：派单后狗不动（实测走通，直接照抄）

前提：派单已产生 `taskId`、`robotState` 已转 `03`（否则先查 §3.3 的四项前置）。

1. **90 秒门禁**：无可见位移即 `stopTask`，不要等平台超时（坑 16）。
2. **查告警表**，看有没有「触发停障告警，前方距离: 0.0X m」：
   - **持续多条** → 假停障，进第 3 步。
   - **只有 1 条后恢复** → 非致命，可重发（12:15 那次即如此）。
   - **一条没有** → 不是避障问题，转查地图加载 / 定位 / 控制链路。
3. **现场目视**狗正前方是否真有物体、镜头是否被遮挡。
   无物却持续报 → 判为假读数（强光或传感器故障）。
4. **Body Control 摇杆原地转向**（分诊关键动作）：
   - 转得动 → 平台到狗的运动链路完好，故障域收敛到避障判断；
     转到面朝空旷/背光方向后**直接重发派单**即可。
   - 转不动 → 才去怀疑控制链路 / 授权 / 机器人本体。
5. 重发后再次执行第 1 步的门禁。

**排除法提醒**：本次曾误判为「遥控器 START 抢占控制权」，让主人关机重启遥控器，
结果狗依然不动——是告警表里的停障记录才指向真因。
**不要凭机理猜测下结论，先把告警表读完。**

## 4. 接口事实修正（推翻/补充既有基线）

| 编号 | 原口径 | 实测 | 处置 |
|---|---|---|---|
| **F8 / E1** | `sendNavigate` 返回不含任务标识，是否产生可查任务待验证，**调用方不得依赖** | 返回体确实无 `taskId`，但约 3 s 内 `getStateData.currentTaskId` 出现 `taskId`，`getPagingRobotTask` 有完整记录 | **E1 结论：可查任务成立**。`is_arrived()` 可走任务记录，不必依赖 DDS 位姿（解开对 Q1 的强依赖） |
| **F6** | `getCurrentByRobotId` 有 `pointsId` / `currentState` / `totalState` / `taskId` / `taskItemId` | 任务执行中调用，**除 `keyName` 外全为 `null`** | 该接口**不可作进度源**，代码里不要再读它 |
| 重定位 | `free/mapUpdate action=1` + `xyth` | 返回 `code=0 操作成功!`，位姿**不变**。前端真正用的是 `POST /model/map-correct-pose`；其错误文案要求 `robotId` + **`mapId`**（我们传的是 `destKeyname`） | `TopseeClient.relocate()` 标注「实测不生效，勿用」；重定位走 UI |
| 成败判据 | `result` 字段 | 任务记 `result=成功` / `alarmCount=0`，**同一秒**告警表有「导航失败·巡检目标被占用」 | **禁止单独用 `result` 判成败**，必须与告警表按时间窗交叉核对 |
| 任务结构 | — | 平台会**自动前插一个合成航点**，`taskItemId = "-10"`，指向当前/充电点。本次那条 `导航失败` 告警正是这个合成段产生的 | 解析 `instruction` 时必须识别并跳过负 `taskItemId`，否则会把合成段的失败当成真实目标失败 |
| G4 / G5 | 无置信度、无实时位姿 HTTP 接口 | `getStateData` 全字段翻遍，**确无位姿字段**；大屏位姿走另一条实时通道（未逆向，疑 MQTT/WebSocket） | 结论维持。人工 `ack_confidence` 仍是唯一手段 |

## 7. 坑清单（按踩坑顺序）

1. **API 前缀与登录格式**：离线一体机是 `/service`，登录走 JSON body + `tuopushi_edge_token`。
   按云端口径调会得 401/400。（已在 client 处理）
2. **不加载地图直接派单 = 静默失败**：返回体看不出任何异常，任务根本不产生，
   线索只在告警表。**任何派单失败排查都必须先查告警表。**
3. **`relocate()` API 假成功**：返回 `操作成功` 而位姿不动（§4）。
4. **`keyname` 取错**：要用 `keyNameMap`。取 `keyname` 会得 `None` 并静默空转。
5. **配色误读代价 6 米**：自制可视化曾用「黄=充电」，平台是「蓝=充电、橙=巡检」。
   据此把巡检点当充电点，重定位定偏约 6 m。**任何涉及点位的沟通都先对齐配色。**
6. **`th` 单位不明**：全部 7 个点位的 `th` 都是 `0`，无法从数据推断弧度还是角度。
   UI Redirect 的两点法天然规避了这个问题——这也是不用 API 的又一理由。
7. **`result=成功` ≠ 真成功**（§4）。
8. **站姿待机功耗约 20%/小时**：09:36 的 64% 到 11:07 只剩 36%。
   现场窗口很贵，**先把动作跑完再写文档**，别让狗站着等分析。
9. **`getStateData` 无位姿字段**：大屏位姿走另一条实时通道，尚未逆向。
10. **DDS 订阅在 WiFi 上 0 样本**（疑 AP 组播隔离），快通道仍阻塞；
    SSH 凭据公司内部已无人掌握，需走厂商客服。
11. **平台未配置充电房/充电桩 → 平台侧看不到任何充电状态**。实测
    `charge/getRoomPageDate` 返回 `total=0`，`charge/getChargeDetail` 报「数据不存在」，
    且 `getStateData` 的机器人记录里**根本没有 `chargeState` 这类字段**。
    P3 那个「充电点(03)」只是点位类型标记，**没有关联任何充电设备**，
    所以 `One Key Return` / `instrument/robotTask/back` 只是把狗走回 P3 坐标，
    平台不会、也无法帮你对桩或确认充电。
    ⚠️ **但充电桩本身是通的**：人工把狗挪到充电板上蹲下后，电量单调上升，
    实测速率约 **10~15%/小时**（11:40–11:58 由 30% 升到 33%；12:23–12:27 由 29% 升到 30%）。
    结论修正：**能充电，只是全过程无平台可见性，得靠人工对位 + 电量趋势判断。**
    ⚠️ D3 数据采集排期仍需把「人工对位充电」计入工期，且从 30% 充到 80% 约需 4 小时。

12. **判断是否在充电，观察窗口必须 ≥15 分钟**。短窗口会被电压回弹骗：
    狗由站姿转蹲姿时负载骤降，电压回升带动百分比虚涨 1~2%，
    看起来像充电但其实不是。本次就先据 6 分钟窗口误判为「没在充电」，
    后经 18 分钟窗口推翻。**可靠判据是长窗口内单调上升，而非单次差值。**

13. **🔴 假停障：正午阳光直射前置深度相机 → 假障碍 → 狗零位移而平台记「成功」**（§1.2）。
    这是本文最危险的一条，因为**失败与成功在平台返回体上完全无法区分**。
    - 识别：告警表出现**持续**的「触发停障告警，前方距离: 0.0X m」，
      而现场目视前方无物。
    - 处置：用 Body Control 摇杆把狗转离强光方向；转向后重发即可正常导航。
    - 预防：**避免让狗停在正对窗户的朝向**；强光时段尽量避开靠窗航段。
    - 工程含义：自动化闭环**必须**有独立于平台的位移校验
      （目视 / 大屏图标位移 / 未来的实时位姿通道），不能只看 `result`。

14. **朝向是功能性的，不只是观感**。狗停下时的朝向决定了下一次派单能不能起步——
    正对强光或近距物体会直接触发持续停障。任务收尾应把狗留在**面朝空旷**的朝向，
    这条要写进后续的收车 SOP。

15. **🔴 严禁用 Redirect 来「复位朝向」**。Redirect（大屏两点法）改的是
    **系统对位姿的估计**，不是狗的**物理朝向**。拿它去把朝向「拧回原样」，
    等于往定位里注入一个与实际不符的先验，会污染刚校准好的定位。
    要物理转向只有两条路：**平台 Body Control 摇杆**，或遥控器手动。
    （本次曾一度给出「到站后再 Redirect 一次复位朝向」的错误建议，已作废。）

16. **操作规范：派单后设 90 秒位移门禁**。参照真实走通的耗时（85~92 s / 6.58 m），
    派单后 90 秒内若狗无可见位移，立即 `stopTask` 中止，不要等平台自己超时——
    实测一次空转会烧掉 183 秒和约 2% 电量，且最后还给你一个 `成功`。
